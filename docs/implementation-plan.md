# USS Race Tracker 实施计划

状态：第 1 阶段近期样本验证、第 2 阶段本地／Sites 最小切片已完成。英文 SPA 位于 `web/`，本地和私有 Site 使用相同代码及 D1/R2 绑定；两场真实比赛样本已分别导入并验证。尚未实现跨比赛身份合并、年龄推算、完整批量导入或图表。详情见 [source-validation.md](source-validation.md) 与 [local-sites-foundation.md](local-sites-foundation.md)。

## 目标与范围

- **最终产品语言（已确认）：全部使用英文。** 页面、导航、表格、图表、帮助、Skating age 解释、无障碍标签、错误提示，以及代码、标识符、注释、测试和运行文档均使用英文，允许英文缩写。对话和本计划可含中文；下文中文文案仅用于讨论，不进入成品。原始运动员姓名、俱乐部名称及来源证据保留原样，不强制翻译。

- 源码保存在本 GitHub 仓库，支持本地开发和 ChatGPT Sites 部署。
- SPA 交互：比赛目录及结果、运动员搜索与 profile、历史成绩列表、单人成绩折线图、同距离多人对比。
- 数据入口：https://www.usspeedskating.org/results
- 目录内 short track 和 long track 均纳入来源盘点；查询、图表按 discipline 分开。
- 仅展示来源可证实的运动员资料；不推算生日或补写个人履历。

## 已核实的来源特征（2026-10-29）

- 页面显示 2014 至 2026–2027 的年度/赛季分组。这是目录范围，尚未验证全部链接可访问或内容完整。
- 展开的 2025–2026 分组有 41 个结果链接，均指向 Contentstack 托管的 PDF。
- 2014 分组包含 `/events/results/2014/...` 旧赛事页面，需要二次发现文件；不是统一的 PDF 直链。

## 技术方案

- 使用 Sites 提供的 React / TypeScript / Vinext 全栈模板，界面采用客户端导航和交互。
- Worker 内提供查询 API；D1 保存结构化记录，R2 保存原始来源文件及必要的导入产物。
- `.openai/hosting.json` 声明 DB / BUCKET，保留 Sites 构建集成。
- 本地使用模板提供的 D1 / R2 模拟环境，线上由 Sites 提供资源；代码和 schema 共用，数据分别导入。
- SQL migrations 只负责结构；种子和真实数据通过独立导入流程写入。
- 大 PDF 的下载、解析和校验先作为仓库内离线工具运行，避免放在页面请求中执行。线上只查询已验证数据。是否增加托管导入任务，待资源和更新需求验证后确定。
- 索引、分页和按运动员/距离/时间范围查询控制返回体积；用真实数据验证性能，不预先承诺延迟。

### 访客站与管理站分离（2026-10-30 已确认）

- 最终成品采用两个独立部署、不同 origin／subdomain 的网页：Viewer 供分享后查看结果；Admin 供明确授权的管理员登录、导入、验证、发布、定时任务及报告管理。保存在同一个代码仓库，分别维护 Sites 身份和访问策略。
- 管理站需平台登录与服务端管理员授权，普通访客不能访问管理内容或调用管理操作；不同域名负责入口分离，真正权限边界由服务端执行。扩大 Viewer 的分享范围不得扩大 Admin 的权限。本轮不更改现有私有站的访问范围，也不创建管理站。
- 开发阶段继续本地 Python 解析；最终迁移到云端后台任务。管理员手动导入和定时导入使用同一验证流程；关闭网页后任务仍能运行。
- 管理站提供导入历史、进度、验证错误／警告、成功与失败项目、发布状态、定时配置，以及完成报告与邮件发送状态。邮件失败与数据导入结果分别记录；报告始终保存在 Admin，支持可追溯重试并防止重复发送。
- 两站之间采用受保护的数据发布契约。尚未验证 Sites 两个项目能否共享同一 D1/R2 绑定，不直接假定共享；若不支持，则将审核通过的版本安全发布到 Viewer 自己的只读数据投影，保留旧有效版本直至新版本完整就绪。
- 独立 Sites 地址可作为初始入口；如使用自有子域名，待域名与 DNS 配置确认后再绑定。云端解析运行环境、邮件服务、管理员名单、定时频率和收件人留到实施时选择与验证。本轮不启动自动任务、不发送邮件。
- 详细要求与验收见 [admin-architecture.md](admin-architecture.md)。

### Admin 独立实施轨道

具体开发步骤见 [admin-implementation-plan.md](admin-implementation-plan.md)，不再只依赖架构说明中的功能清单：

1. **A0：能力与契约验证**——确认独立站点身份权限、两站数据发布路径及导入批次契约。
2. **A1：独立 Admin 站点与登录授权**——建立管理站项目、导航与服务端管理员权限。
3. **A2：导入批次与验证后端**——接入主站第 3 阶段形成的导入契约，提供管理站所需的批次工作流。
4. **A3：手动导入与审核页面**——查看进度、成功／失败、原始页码和待处理问题。
5. **A4：向 Viewer 发布已验证版本**——校验、完整发布、读回验证及失败保护。**A1–A4 构成第一版可用管理站。**
6. **A5：云端解析任务**——迁移可移植 Python 流程，验证关闭浏览器后仍可运行。
7. **A6：定时导入配置与执行**——在已验证的后台任务基础上加入调度、暂停及去重。
8. **A7：邮件报告与发送历史**——验证实际投递，区分导入／发布／投递结果并支持安全重试。

用户已明确当前继续主网站，不建设 Admin 网站。A0–A7 保留为后续独立轨道；不能把它们当作当前主站阶段的下一步。主站先建立自己的受保护导入接口与验证流程，未来 Admin 再接入；不创建管理站项目、域名、页面、登录或调度。

## 分阶段交付

### 1. 来源清单与解析验证

盘点所有赛季的目录项，保存标题、赛季、入口 URL、文件 URL、访问状态、格式与更新时间。抽样验证近期短道、近期长道、普通地区比赛和历史页面。

提取原始文件并记录内容 hash、解析器版本、页码和异常。区分参赛名单、总排名、单距离汇总、逐场结果，防止重复计数。验证日期、距离、计时精度和异常状态。不能解析的文件进入待处理清单。

验收：来源清单可复查；短道和长道各有经过人工抽查的结构化样本；格式差异、损坏链接和待处理项有记录。若某格式尚无法支持，明确覆盖范围后继续。

### 2. 本地到 Sites 的最小部署

在本仓库建立模板、一个真实样本查询 API 和简单页面，连接本地 D1；创建私有 Site 并部署，验证线上 API、数据库迁移和直接访问路径。验证 R2 样本存取及独立数据导入路径。

验收：同一份源码可在本地和 Sites 读取样本；记录可复现的启动、构建和部署命令。实施该阶段时才创建 Site；规划和来源验证阶段不创建。

### 3. 数据模型与可靠导入

初步实体：skaters、skater_aliases、competitions、competition_entries、events、races、results、classifications、source_documents、import_runs。字段和拆分以第 1 阶段样本验证为准。

本阶段先实现主网站的候选导入批次、逐项验证报告和生效数据版本。后台 job、schedule、notification 与管理站审计界面属于后续 Admin 轨道，本轮不实现。当前样本 seed 接口不等于正式管理后台；数据发布前必须经过验证，失败批次不能替换 Viewer 正在使用的有效版本。管理员手动导入、未来云端定时导入共用同一生命周期，具体流程见 [admin-architecture.md](admin-architecture.md)。

**当前阶段的赛季约束（2026-10-30 用户补充确认）：** season 与 discipline 共同定义比赛目录的查询范围，不能等到页面设计时才作为可选筛选补上。正式比赛数据必须有经过核对的赛季归属，保留原始来源赛季标签；不直接用比赛标题中的单个年份代替赛季。目录 API、搜索、分页、计数及索引设计均按选中的 `discipline + season` 组织。资料不足、赛季未确认的记录进入待核对流程，不混入已确认赛季。个人跨赛季资料的浏览规则留待后续讨论，不属于本次目录决策。

- 参赛编号先按比赛作用域保存，未证实前不作为全球运动员 ID。
- 名字、俱乐部和年龄组保留原始值与历史参赛记录；同名和拼写变体需要可审查的映射，不只按姓名自动合并。
- 原始用时与精确整数计时单位并存；单位以实际来源精度确定。
- 保留 discipline、distance、round、heat、race、division、状态和来源页码。
- 分离逐场结果与汇总排名；对更正文件保留来源版本，替换当前生效记录。
- 以来源 hash、来源局部标识和受控导入流程实现可重复导入；写入接口需要服务端授权。

验收：重复导入不增生数据；更正可追踪；缺失、歧义和解析失败不静默丢弃。

### 4. 比赛和运动员浏览

#### 比赛目录扩展方案（2026-10-30 已确认，更多数据导入时实施）

本节记录已确认的正式目录交互，暂不替换当前两场比赛的 sample tile 布局。扩展比赛／赛季数据时按以下方案调整；不把当前样本布局推广成历史目录。

- 比赛入口使用独立的 **Short Track / Long Track** 切换，取消比赛目录的 `All disciplines`；各入口只展示、搜索和查询对应 discipline 的比赛。
- 默认选择当前 discipline 中最近一个有数据的赛季，并明确显示所选赛季；支持切换历史赛季。赛季筛选与搜索共同生效，搜索范围明确为当前 discipline／赛季。
- 比赛目录始终明确选中一个 season，不提供默认跨赛季混排的 `All seasons` 视图。选择 `2025–2026` 后，列表、搜索结果、分页和数量统计只包含该赛季，不夹入 `2024–2025`；切换赛季时重置页码并退出不属于新范围的比赛详情。选定赛季没有匹配结果时显示空状态，不静默回退到其他赛季。
- 比赛目录采用可筛选、分页的列表：桌面为表格，手机为紧凑列表。主要字段为日期、比赛名称、地点，按比赛日期从新到旧排列；人数与成绩数量等细节放入比赛详情。
- 默认每页约 25 场比赛，服务器执行筛选和分页，避免浏览器一次加载全部历史目录。
- 点击一场比赛进入 SPA 内的比赛详情，再选择组别／性别、距离和轮次，查看同一竞争项目的全部 heats；继续遵守下述成绩聚合规则。
- discipline、赛季、搜索词、页码与选中的比赛写入 URL。刷新、分享和浏览器前进／后退均恢复对应状态；从详情返回目录时保留筛选、页码与列表位置。
- 个人 profile 的跨赛季／跨 discipline 展示留待后续单独讨论；比赛目录的单赛季范围不直接套用到个人历史记录，也不在本轮扩展个人视图。
- 正式界面文字全部为英文，例如 `Competitions`、`Season`、`Search competitions…`、`Date`、`Competition`、`Location`、`Previous`、`Next`。

验收补充：短道／长道目录相互独立；每个入口的默认赛季确实有数据；搜索不跨出当前筛选范围；分页由服务端执行；URL 和返回导航保留状态；桌面与手机均能高效浏览大量比赛。本次仅记录决策，不立即修改或部署页面。

**成绩聚合规则（用户已确认）：默认按同一赛事、discipline、组别／性别、距离、轮次及来源项目标识汇总全部 heats，不能默认只展示一个 heat。** 同一个女子／男子项目的多个 heats 在同一张表比较；Women NEST 与 Men NEST 等不同竞争组分别显示。Quarter-final、Semi-final、Final 不混合；同距离重复项目也依据来源标识分开。提供项目／轮次选择，保留每条记录的原 heat、heat 内名次和来源页码。跨 heat 的用时排序必须标明是比较顺序，不当作官方总排名；晋级与判罚按原始记录保留。导入器必须验证全部声明的 heats 已齐全，缺失时不能宣称该项目完整。

实现比赛列表、赛季/discipline/距离筛选、比赛结果、运动员搜索、profile 与成绩列表。每条结果可返回比赛及原始来源。资料缺失显示未提供。

验收：比赛 → 运动员 → 历史成绩路径完整；搜索、分页和空状态可用；手机可读。

### 5. 曲线与多人对比

横轴为比赛日期，纵轴为用时，日期缺失或仅能确定比赛范围时明确标记，不编造逐场日期。支持同 discipline、同距离多人对比和轮次/时间范围筛选。

保留全部有效出场点；另提供每场比赛最好成绩视图，避免同日多轮连线误读。PEN、DNS、DNF、DQ 等保留原始状态并按已核实规则决定图表资格，不画成零用时。赛道规格在有数据时保存并提供筛选。

验收：图表点与列表一一对应；提示信息含比赛、轮次、用时与来源；不同 discipline / 距离不会被混画。

### 6. 扩大覆盖与正式交付

逐赛季扩展解析器和导入，显示已覆盖赛季、比赛数量、最后更新与未解析范围。测试关键解析规则、身份映射、幂等导入、查询和图表数据；对真实大数据量测量性能。

完成桌面/手机浏览器检查、生产构建及私有部署验证，保存 README、数据字典和导入操作说明。公开访问或定时自动更新作为后续明确选择，不默认增加。

## Profile 与参赛年龄设计补充

此处“滑冰年龄”指赛季参赛年龄（racing age），不是开始滑冰至今的年数，也不等同于当前实际周岁。用户已确认下述推算、展示及每年 7 月 1 日自动增长规则，实施时作为验收要求。

### 进一步抽查结论

- 2026 ST AGN 名单列为 `# Name Status Gender Division Club`，Status 提供 JR C、JR D、SR、35+ 等类别；不直接给出每个人的单岁年龄。
- 2026 US ST Championships（实际比赛日期 2025-09-11 至 14）名单也有 Status 和 Club，Division 为 Group A/B，不能把该比赛分组当作年龄组。
- 2026 MASA 名单列为 `# Name Gender Division Club`，没有 Status 或具体年龄；DeClemente、Heo、Kim 等 Division 不可直接映射年龄。
- 上述样本足以支持姓名、参赛所属俱乐部/注册归属、成绩档案；年龄完整性依赖其他比赛证据。长道名单已补充验证，全部历史文件尚未验证。
- `Direct` 原样保存为注册归属，不当成俱乐部名称；俱乐部按参赛日期保留历史，profile 显示最近一次记录及日期，不宣称为已核实的当前归属。

### 年龄推算规则（拟实现）

1. 保存每一条年龄证据的比赛日期、年龄基准日、原始值、规则版本、来源页码和运动员映射依据。具体年龄、年龄组、出生日期分开记录；缺失不编造 DOB。
2. 为每项比赛/赛季确定适用规则。已核实 2025–2026 长道 AGN 规则用 2025-07-01 之前的年龄，短道 AGN 公告也以 2025-07-01 为基准；7 月 1 日边界的 before/as-of 差异须按适用正式规则明确，不能自动混用。不能把本赛季规则倒套全部历史比赛。
3. 只有明确的个人年龄类别可转换为区间；能力组、合并比赛组、成绩用时不能作为年龄推算依据。对已核实同一年度基准体系的记录，将各赛季区间平移到统一参考赛季，再求交集。
4. 单一可能年龄显示为“推算参赛年龄”；多个可能值显示范围；缺乏证据显示“未提供”；交集为空标记冲突，检查身份误合并、解析、规则和源文件更正，不以最新文件覆盖或取平均。
5. 示例（假设已确认该规则 JR C=13–14）：2024–2025 为 JR C，则到 2025–2026 为 14–15；2025–2026 仍为 JR C，则交集为 14。2026–2027 推算为 15。这一唯一值仍依赖来源和规则正确，不等同于官方生日认证。
6. profile 保存参考赛季和确定值/可能范围，查询时计算当前赛季值。产品统一在每年 7 月 1 日切换参赛年龄赛季并加一；7 月 1 日至次年 6 月 30 日为一个周期，不在生日、自然年 1 月 1 日或比赛文件上传日加一。使用固定的 America/New_York 时区（7 月 1 日 00:00 切换），避免访客设备时区不同导致结果不同。历史成绩保留当时的参赛年龄证据；采用不同基准的来源先按第 2 条核实、归一化，不能直接参与统一推算。
7. 已核实的基准不会被单条矛盾数据自动覆盖；更正通过可追溯的复核流程更新，支持纠正而非永久冻结错误。只有年龄范围时也随赛季整体平移，不能自动选择范围中点。

### 页面展示与解释（已确认）

- 标签统一使用 **Skating age**，中文为“参赛年龄”；不单独使用容易混淆的 Age。“Ice age”作为用户讨论中的同义称呼，不作为另一套算法或页面字段。
- 标签旁设置可聚焦的信息按钮（例如 ⓘ），提供清晰的无障碍名称。鼠标 hover、键盘 focus，以及点击/手机 tap 都可打开解释；点击/tap 后可保持展开并关闭，不能只有 hover 才能阅读。
- 默认英文解释文案：`Skating age is your season-based competition age, not your current age or years of skating experience. It increases by one each July 1. Values are based on published competition records and may be inferred or shown as a range when the records are incomplete.`
- 中文解释文案：“参赛年龄是按赛季计算的比赛年龄，不是当前实际周岁，也不是学习滑冰的年数。每年 7 月 1 日统一增加一岁。年龄依据公开比赛记录计算；资料不足时可能显示推算值、范围或未提供。”
- 示例展示：`Skating age ⓘ 15 · Inferred · 2026–2027`；范围为 `14–15 · Estimated range`；无有效证据为 `Not available`；冲突未解决时明确标注 `Needs review`，不把争议值当作已确定年龄。
- 详情可查看参考赛季、来源和依据；已直接提供的明确参赛年龄与跨赛季推算值分别标记。DOB 可空，不要求填写、不从范围虚构出生日期。
- 在 profile 与成绩详情中明确区分“当前赛季参赛年龄”和“该场比赛当时的参赛年龄”。
- 页面跨过 7 月 1 日时应刷新派生值（定时或重新聚焦时校验），缓存也必须按赛季失效；无须用户重新导入 PDF。由参考赛季计算而非每年累加写回数据库，避免重复执行导致多加岁。

验收补充：同赛季多赛事一致、跨自然年不误加岁、6 月 30 日至 7 月 1 日边界、不同客户端时区一致、页面跨赛季刷新、范围两端同时增长、跨年年龄组取交集、能力分组无效、来源冲突、同名误合并与俱乐部变更均有覆盖。解释须支持 hover、键盘和手机 tap，推算状态不能省略。
